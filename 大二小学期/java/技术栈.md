## 一、技术栈选型

**核心原则**：这个项目的难点不在 CRUD，而在"并发抢座 + 超时释放 + 实时推送"这三块。技术栈要服务于这三个点，其余从简。

后端建议：

- **JDK 21（LTS）+ Spring Boot 3.5.x**。说明一下版本：现在最新是 Spring Boot 4.1（基于 Spring Framework 7，今年 6 月发布），但国内常用的 MyBatis-Plus、Sa-Token、Knife4j 等生态库对 SF7 的适配还参差不齐，课程项目用 3.5.x 教程最多、踩坑最少。想秀"用了最新版"可以上 4.0/4.1，但要预留调依赖的时间。
- **MyBatis-Plus** 做 ORM（比纯 JPA 在国内项目里更省事，分页、逻辑删除开箱即用）。
- **MySQL 8** 主存储。
- **Redis 7** ——这是重点，同时承担三个角色：分布式锁、缓存、热力图实时状态。
- **Redisson**：分布式锁 + 延迟队列（超时释放靠它，下面讲）。
- **Sa-Token** 做认证鉴权（轻量、国内文档全，区分普通用户/管理员角色比 Spring Security 配起来快得多）。
- **Knife4j** 自动生成接口文档（答辩时打开一看就很专业）。

前端建议（按你时间决定）：

- **管理端**：Vue 3 + Vite + Element Plus + **ECharts**（热力图和报表全靠它）。
- **学生端**：两条路——图省事就也用 Vue 3 Web；想要"校园 App"的观感就用 **uni-app 做微信小程序**。一个人做的话强烈建议学生端也用 Web，省一套环境。

部署：**Docker Compose**（MySQL + Redis + 后端 + Nginx 一键起），答辩时"我已经容器化部署"是个小加分。

## 二、三个核心难点的解法（这是出彩的本体）

**1. 并发抢座** — 必须做对，也是被问最多的点

分层来讲，答辩时能展开一整套：

- **正确性兜底**：`reservation` 表对 `(seat_id, date, time_slot)` 建**唯一索引**，再用乐观锁 CAS 更新座位状态：`UPDATE ... SET status=占用 WHERE seat_id=? AND slot=? AND status=空闲`，判断 affected rows。这一层保证"绝不超卖"，无论并发多高。
- **性能优化层**：抢座前先用 **Redisson 分布式锁**（锁 key = 座位+时段）或 Redis Lua 脚本原子预占，把无效请求挡在数据库之前。

老师一问"两个人同时点同一个座位怎么办"，你能从唯一索引讲到乐观锁讲到分布式锁——这是整个项目密度最高的加分点。

**2. 超时未签到自动释放** — 别用"每分钟扫全表"

- **入门做法**：`@Scheduled` 定时任务每分钟扫描过期未签到的预约 → 释放。能用，但答辩时主动指出它的缺陷（扫全表、精度差、不可扩展）会显得你想得深。
- **出彩做法**：预约成功时把"签到截止时间"作为 score 丢进 **Redis ZSet（或 Redisson DelayedQueue）**，到点精准触发释放 + 累加爽约次数。把这条对比讲出来，就是一个完整的技术故事。

释放逻辑要和**黑名单**联动：自动释放触发时给用户 `no_show_count + 1`，达到阈值就写 `blacklist_until`，预约接口前置校验拦截。

**3. 实时座位热力图** — demo 的视觉爆点

- 用 **SSE（Server-Sent Events）** 而不是 WebSocket：座位状态是"服务端→客户端"单向推送，SSE 完全够用且更简单。某座位被占/释放 → 服务端推事件 → 前端 ECharts 网格对应格子变色。
- 座位排布用"行×列网格 + 单元格类型（座位/过道/空）"建模，管理端录入时画格子，学生端选座、热力图展示**复用同一套网格数据**。
- **答辩时两个客户端并排，一边点预约，另一边格子实时变红**——这个画面比任何 PPT 都有说服力。

## 三、数据模型（核心表）

```
campus(校区) → building(楼栋) → room(自习室, 含开放时段) → seat(座位, row/col/类型)
reservation(预约): user_id, seat_id, date, start/end_time, 
                   status[待签到→使用中→已完成 / 已取消 / 已过期释放], sign_in_time
user: student_id, phone, role, no_show_count, blacklist_until
daily_stats(报表): room_id, date, usage_rate, peak_hour ...
```

状态机讲清楚也是加分项：`待签到 →(签到) 使用中 →(到点) 已完成`；分支 `→(用户取消) 已取消` / `→(超时未签到) 已释放 + 爽约+1`。

## 四、分阶段落地计划

按依赖顺序，每个阶段都是可演示的完整切片，避免做到一半跑不起来：

- **P0 脚手架**：建库建表、Docker Compose、Sa-Token 登录骨架、Knife4j。
- **P1 基础 CRUD**：管理端录入校区/楼栋/自习室/座位排布；用户注册（学号认证）。
- **P2 核心预约**：按校区/楼层筛选 → 选空闲座位 → 预约（唯一索引 + 锁）+ 单日次数限制。**做到这里项目就能跑通主流程了。**
- **P3 座位管控**：签到、临时取消、超时自动释放（延迟队列）、爽约黑名单。
- **P4 实时热力图**：SSE 推送 + ECharts 网格可视化。
- **P5 数据报表**：定时聚合 `daily_stats` + 使用率/热门时段图表。
- **P6 打磨**：可选 AI 模块（用历史数据给"此刻空位概率最高的自习室"推荐）、部署、写答辩演示脚本。

把 P2 当 MVP 红线——**先保证主流程跑通，再往上叠 P3–P5 的亮点**，时间不够就砍 P6 和报表的精细度，绝不动 P2–P4。
